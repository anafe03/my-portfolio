How TM GO works today — and the refactor.

Today the bot is a ReAct agent: one big loop where the model decides each step. The refactor makes it an explicit StateGraph — a router that sends each message down a fixed pipeline. Both diagrams below are drawn from really-compiled graphs. Click any node to see what it does.

One loop, the LLM drives

The live bot (create_react_agent). Every turn the model reads the whole chat, decides whether to call a tool or reply, and loops — capped at 3 tool calls. There's no fixed path; the behavior lives in a ~300-line system prompt.

The guardrails that keep the loop honest — all prompt rules
Never claim an untaken action
It can't say "sent" unless it actually called send_last_draft this turn.
Follow through on "yes / send it"
A confirmation triggers the send immediately — no "which email?".
Resolve the active venue
Pronouns ("the wifi", "send it") resolve to the venue from recent turns.
Never fabricate data
Every fact must come from a tool result — no invented contacts or times.
Don't loop
≤3 tool calls per turn; never the same tool twice with the same args.
Refactor · one graph, three business functions

Docs in · Email · Questions — around the sheet

Everything TM GO does is three jobs, all revolving around the Google DB (system of record): 📄 Docs in (upload → parse → ⏸review → write), ✉ Email (assess what's missing → draft → ⏸approve → send; replies come back in and update the DB), ❓ Questions (read → answer) — plus a tool loop for everything else. Two human gates: review-before-write and approve-before-send. The amber trail below is a real "advance a show" run.

🔘 Buttons = deterministic — a button knows its intent and enters at its node, skipping the router. 💬 Chat = free-form — the router classifies it. Same graph either way.

Why this shape?
One shared core, two doors: chat runs the graph, the app's buttons call the same nodes. The LLM only drafts & parses; the approval gate is a real interrupt(), not a prompt rule; and send is pulled out of the tool loop so the cycle can read / draft / log but never send.
The safety win

The approval gate is structural, not a prompt rule

Advancing spans draft → send. Today the ReAct bot can fire the send on an LLM "send" classification. In the StateGraph, send has one inbound edge — from an interrupt() a human must resume. Draft = LLM · Approve = human · Send = code. No router or LLM path can reach send.
